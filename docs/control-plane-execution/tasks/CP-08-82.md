# CP-08-82 — Scope the Paperclip acceptance spike

- **Status:** in review

## Outcome

The charter §4 acceptance spike has a written plan —
**`PAPERCLIP_SPIKE_PLAN.md`** — naming every piece before any code is
mirrored:

- **What runs where.** The downstream Paperclip plane (local, PGlite)
  on one side; an authenticated ALTAI host process on the other. The
  bridge between them is a **named downstream package**
  (`packages/adapters/altai-host`) riding Paperclip's adapter registry
  seam (`server/src/adapters/registry.ts`, the same seam
  `claude-local`/`codex-local` ride), speaking ALTAI's authenticated
  transport on its execution side. This is the charter's "replacing
  its execution adapters with ALTAI host/IsanAgent adapters over a
  versioned protocol" made concrete.
- **The wire it rides.** Nothing new: 051 negotiate → 024 wake/claim →
  checkout → 034 IsanAgent attempt → 035 events → 045 Review. Every
  step cites the contract that already shipped.
- **The harness is the only pass path.** An `altai-cli` subcommand
  (`paperclip-spike`), not a hand-run demo: it provisions the fixture,
  drives dispatch → checkout → execute → review, executes the
  reconnect drop itself, and asserts the 020–024 idempotency
  invariants and the 045 Review gate. Exit non-zero on any break.
- **Remaining 080 PRs are named:** CP-08-83 (downstream adapter
  skeleton), CP-08-84 (the harness against a stub plane), CP-08-85
  (end-to-end against the real downstream; spike evidence; 080
  acceptance).

## Rationale

- **Scoping before code.** The charter's §5 fence — no Paperclip
  source into Apache artifacts from the charter alone — means the
  first ALTAI-side decisions about where the bridge lives and what it
  implements should be reviewable on paper, exactly as the charter
  itself was.
- **The harness is the deliverable.** "A demo run makes nothing
  production-critical" is only enforceable if the pass evidence is a
  reviewed, typed harness output rather than an operator's transcript.
