# CP-08-73 — Declarative plugin UI schema contract

- **Package:** 073 — Schema-driven/sandboxed plugin UI (PR 1)
- **Status:** in review
- **Depends on:** 071 (#787, #789), 072 (#815–#818, #820)

## Outcome

A plugin's UI is now a schema the host renders, not code the host runs.
`PluginManifest` gains an optional `ui: PluginUiDeclaration` — named,
titled surfaces, each a tree over a closed node vocabulary
(`section`/`text`/`table`/`action`). The only interactive node, `action`,
names a host-side operation (`invoke_job`) — never a script, a URL, or
markup. There is nothing in a `PluginUiNode` to execute.

Validation happens at registration, against the manifest's declared
capabilities: the declaration requires `PluginUi`; an `invoke_job`
action requires `Jobs`; and structural rules make every declaration
unambiguously renderable — bounded depth (8) and size (256 nodes per
surface, 16 surfaces), unique non-empty surface ids, table rows exactly
as wide as their columns. Because the declaration rides in the
manifest, the registry's existing `validate()` path refuses an unsound
UI before storage, and the 071 upgrade rules cover it for free: a
changed UI at the same version is refused, an upgrade that expands
capabilities still needs accepted disclosure.

This is the static half of the 073 gate ("UI cannot bypass worker
capability checks"). The runtime half — the dispatch path refusing what
the capability check refuses, whatever the client sends — is PR 2.

## Rationale

- **The vocabulary is the sandbox.** Sandboxing by filtering unsafe
  things is a losing game of enumeration; a closed vocabulary with no
  escape hatch starts safe. Bounds (depth, node count, table shape)
  make a declaration cheap to trust — a bounded tree cannot be a
  layout bomb.
- **Actions name operations; the host executes.** `invoke_job` says
  *what*, never *how*: dispatch travels the 072 worker path — at most
  once, ever — so a UI action inherits every guarantee jobs already
  have.
- **Capability is checked statically at registration.** An action whose
  required capability is undeclared is a manifest inconsistency, not a
  runtime surprise: `required_capability()` is per-variant static —
  there is no action whose requirement is computed.
- **In the manifest, not beside it.** A separate UI record would need
  its own storage, versioning and upgrade semantics; riding the
  manifest gets idempotent install, forward-only versions and
  disclosure-gated expansion with zero new rules. The field is
  `#[serde(default)]`, so every stored manifest decodes unchanged.
- **One validation order, both sides.** Rust and the TS mirror run the
  same checks in the same order, so the same declaration reports the
  same first error on both sides — pinned by mirrored tests.

## Scope

- `altai-control-protocol/src/plugin_ui.rs` (new): declaration, surface,
  node, action types; bounds constants; `PluginUiError`;
  `validate(capabilities)`; 8 tests.
- `plugin.rs`: manifest field + `InvalidUi` error variant + validation
  hook; module doc updated.
- `altai-control-plane/src/plugin_registry.rs`: registration-refusal
  test (unsound UI stored nowhere; sound one installs).
- Manifest literals across `plugin_worker*.rs`/`transport.rs` tests
  gain `ui: None`.
- TS mirror: `plugin-ui.ts` (types, bounds, `validatePluginUi`), the
  `ui?` manifest field with the `invalid_ui` branch, exports, and
  `plugin-ui.test.ts` (8 tests) plus a manifest-hook test.
