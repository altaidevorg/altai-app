# CP-08-58 — Scheduled-work projection over routine aggregates

**Status:** complete
**Backlog package:** 066 (Inbox, My Work, routines and recovery UI) —
PR 1 of 2–3
**Depends on:** package 041 (routine aggregates, cron bridge,
materializer), package 060 (server projections answer operational
queries), the Work OS Home surfaces (062–065)

## Outcome

Scheduled work becomes readable where Work lives. Home's right pane
gains a fourth tab — **Work | Agents | Audit | Routines** — and the
Routines tab renders the workspace's routine aggregates, each row
joined with its current intent and firing state:

- **What is scheduled**: the cron expression (mono) or the event
  source, the target Work (title when the bridge has a mapping, raw
  canonical id otherwise), and the lifecycle state — paused and
  retired routines stay visible; silencing a routine is not deleting
  the fact that it exists.
- **When it fires next**: computed with the materializer's own anchor
  semantics (`last_fired`, else the revision's creation), through the
  same `cron_due::next_fire_after` the bridge uses — what the surface
  shows as next is what the bridge will do next. A next fire in the
  past is **overdue** and renders in red ("2h overdue"): the bridge
  has not caught up on it, which is a fact to surface, not hide.
- **What it has done**: the last materialized fire, relative.
- **Read-only**: lifecycle moves (create, pause, retire, revise) stay
  control-plane commands; the surface is a projection, not an editor.

## Rationale

Routine aggregates have been durable in `work.db` since package 041 —
`SqliteRoutineRepository` for writes, the cron bridge and tested
materializer for wakes — but the desktop had no way to read them.
That is the recurring CP-08 shape: the producer exists, the read side
is missing, so PR 1 is the read side. Two repository gaps surfaced and
closed where the semantics live:

- `RoutineRepository::list_all()` — `list_active()` filters to Active
  for the bridge's scan, which is right for materialization but wrong
  for a projection: a paused routine must not vanish.
- `LegacyWorkBridge::legacy_id_for()` — routine targets are canonical
  control-plane `WorkItemId`s; the desktop WorkStore holds legacy ids.
  The bridge owns the one-way mapping table, so the title join
  resolves through a reverse lookup. A target without a mapping (the
  cutover has not projected it yet) keeps its raw id and is simply not
  drillable — honest, and it lights up when package 101 lands.

## Scope

- `altai-control-plane routine_repository.rs`: `list_all()` on the
  trait and the Sqlite impl (list_active now filters over it), + test
  (paused/retired stay readable, active scan unchanged).
- `altai-control-plane legacy_work_bridge.rs`: `legacy_id_for()`
  reverse lookup over the mapping table.
- `altai modules/routines.rs` (new) + `modules/mod.rs` + `lib.rs`:
  `RoutineDto` and the `routines_list` command — work.db opened
  through the store's migration lifecycle, repo and bridge on the same
  file, pure `project_routine` (anchor semantics shared with the
  materializer, malformed cron degrades to no next fire, missing
  intent schedules nothing). Tests: anchor on last fire vs revision
  creation, event trigger, malformed cron, intent-less routine.
- `altai modules/work.rs`: `open_store`/`authorized_workspace` become
  `pub(crate)`; `resolve_work_db()` extracted for companion readers.
- `packages/host-contract types.ts`: `Routine`.
- `src/modules/ai/lib/native.ts`: `routinesList` binding.
- `work-board/lib/routinesProjection.ts` (+ tests): overdue-first
  ordering (recurring by next fire, then event-triggered newest
  first, then intent-less), `formatScheduleTime` ("in 3h" /
  "2h overdue"), drillability gated on a resolved title,
  `summarizeRoutines` page counts.
- `work-board/RoutinesPanel.tsx`: load/retry/empty/list surface with
  summary header; drillable rows open the target Work.
- `DesktopHome.tsx`: fourth `SurfaceTabs` entry; Routines renders in
  the right pane; opening Work returns to the Work surface.
- `WORK_OS_PROGRAM_BACKLOG.md`: 066 → `in_progress`.

## Out of scope

- **Routine mutations from the desktop** — creating, pausing or
  revising routines stays with control-plane commands; bringing the
  write path into the embedded host is a single-writer/cutover
  question (package 101), not a read-side PR.
- **Recovery visibility** — the restart-recovery pass already runs
  inside Work commands and its facts land in the runs hub and audit
  feed; a dedicated recovery view is 066 PR 2 if the existing
  projections prove insufficient.
- **My Work refinements** — the Work surface already lists active work
  (`my_active`) with drillable rows; assignment-scoped views wait for
  an assignment producer beyond `assignee_ref`.
