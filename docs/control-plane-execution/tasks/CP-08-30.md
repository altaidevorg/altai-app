# CP-08-30 — Evidence-gated completion gate

**Status:** done
**Backlog package:** 045 (second PR)
**Depends on:** CP-08-29 (package 045 evidence store), CP-08-18/19 (package 035 — terminal attempt)

## Outcome

Closes the first clause of the 045 gate — **"Completion requires evidence/review"** —
with a completion gate that consumes a terminal attempt and moves a Work item to
`Done` only when its requirements are met: the named attempt succeeded and
belongs to the work item, and the work item has recorded evidence. This is the
"consume the terminal Attempt to move Work disposition explicitly" step the
`finalize_attempt` doc-comment defers to this package — finalization produces
the verification signal (a terminal attempt); the gate moves Work disposition.

When a requirement is unmet the gate returns `Blocked` with the reasons and
leaves the Work item untouched. When the work item is already `Done` the gate is
idempotent. Nothing here governs delivery actions (the gate's second clause) —
that lands in a follow-up PR.

## Rationale

A quality gate that only *checks* requirements but never moves Work does not
make completion *require* anything — unlike the budget enforcer (whose producer
does not yet exist), the inputs here are real: `finalize_attempt` produces
terminal attempts and the evidence store records artifacts. So the gate both
evaluates and enacts, transitioning Work to `Done` via the work item
repository's optimistic-concurrency `replace_if_revision`. The caller supplies
the specific `attempt_id` (the observer that saw the run succeed knows it), so
no attempt-list query is needed.

Evidence presence is checked at the work-item level (`list_for_work` non-empty):
a work item with evidence from any of its attempts has evidence. A per-attempt
evidence requirement is a future refinement (YAGNI).

## Scope (this PR)

- `altai-control-plane/src/completion_gate.rs`: `CompletionGate` holding
  `Arc<dyn WorkItemRepository>`, `Arc<dyn AttemptRepository>`,
  `Arc<dyn EvidenceRepository>`.
  - `complete(&self, work_item_id, attempt_id, updated_at: String) ->
    Result<CompletionOutcome, CompletionError>`.
  - Guards: attempt exists, `state == Succeeded`, `work_item_id` matches;
    `list_for_work(work_item_id)` non-empty.
  - Satisfied → transition Work to `Done` / `ExecutionPhase::Terminal`,
    `revision.next()`, `updated_at`, via `replace_if_revision(work, work.revision)`.
  - Already `Done` → idempotent `Completed`.
  - Unmet → `Blocked { blockers }`, Work unchanged.
- `CompletionOutcome { Completed, Blocked { blockers } }` — the caller reads
  the post-transition Work item back from the repository (it passed the id).
  `CompletionBlocker { AttemptNotSucceeded { attempt_id }, MissingEvidence {
  work_item_id } }`; `CompletionError` wrapping the three repository errors.
- `lib.rs` export. No protocol change (reuses WorkItem/Attempt/Evidence).

## Out of scope (follow-up PRs)

- Governed delivery actions (clause b: delivery requires approval — package 042).
- A `Review` sign-off requirement and per-attempt evidence scoping.
- Transport route / scheduler invocation of the gate.

## Invariants

- A Work item reaches `Done` only via a succeeded, matching attempt with
  recorded evidence.
- The gate never mutates Work when `Blocked`; it returns the reasons.
- Already-`Done` is idempotent (no re-transition, no revision advance).
- The transition uses optimistic concurrency (`replace_if_revision`); a stale
  revision fails rather than clobbering a concurrent change.
