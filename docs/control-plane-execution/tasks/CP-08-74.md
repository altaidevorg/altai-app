# CP-08-74 — UI action dispatch enforces the capability boundary at runtime

- **Package:** 073 — Schema-driven/sandboxed plugin UI (PR 2, closes the
  gate scope)
- **Status:** in review
- **Depends on:** CP-08-73 (#822), 072 (#815–#818, #820)

## Outcome

The runtime half of the 073 gate. `SupervisedWorker::invoke_ui_action`
is the one path a UI trigger takes: it resolves the trigger against the
**installed manifest's** declaration — `PluginUiDeclaration::declares_action`
is the whitelist — and then dispatches through the ordinary jobs path,
which re-checks the capability and the at-most-once ledger. A client
can invoke what was declared, and nothing else:

- an unknown surface, or an action the surface never declared, is
  `WorkerError::UiActionNotDeclared` — before anything is recorded, so
  a refused trigger burns no job id;
- a manifest without a UI declaration refuses every action;
- a hand-crafted manifest (declares a UI, never declared `Jobs` — one
  the registry would refuse at registration) still cannot dispatch: the
  capability check lives at the dispatch boundary, not in the client's
  good behavior — `CapabilityMissing`, nothing recorded;
- a repeated trigger — a double-click — answers `AlreadyKnown`: the job
  was sent once, ever, and the second click changes nothing;
- a dead worker answers `WorkerDown`, unrecorded, retriable.

The dispatch itself inherits everything 072 built: at-most-once by
`job_id`, real stdio to a real worker process.

## Rationale

- **The declaration is the whitelist.** Registration validated it; at
  runtime, the same bytes decide what is invokable. Equality with a
  declared action node is identity enough — an action's identity is
  what it does. No ids were added to the schema for this: the
  declaration already names everything.
- **Runtime does not trust registration.** The registry refusing an
  inconsistent manifest is the static half; the dispatch path re-checks
  the capability on its own, so a manifest that reached a worker
  without passing registration still cannot exercise an undeclared
  capability. Defense in depth, and the gate sentence made literal.
- **One path, every guarantee.** `invoke_ui_action` has no send of its
  own — it routes into `dispatch_job`, so idempotency, capability
  refusal, and `WorkerDown` semantics are not re-implemented beside the
  UI, they are the UI's.
- **Refusal is cheap and total.** An undeclared trigger touches no
  ledger, no process, no state: refused means nothing happened.

## Real-process testing

The jobs child counts its requests, so the double-click proof observes
the worker, not the host's bookkeeping: trigger once, complete, trigger
again (AlreadyKnown), then ask for the count — two requests total
(job + report), the second click sent nothing. Also real: the declared
action round-tripping over stdio to a completed job; the dead-worker
case against a crash-mode child. Pure but pinned: undeclared job on a
declared surface, declared action on an unknown surface, no-declaration
manifest, and the hand-crafted no-Jobs bypass attempt.
