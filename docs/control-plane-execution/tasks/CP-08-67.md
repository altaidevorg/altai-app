# CP-08-67 — Plugin worker supervision core

- **Package:** 072 — Out-of-process plugin workers (PR 1)
- **Status:** in review
- **Depends on:** 071 (manifest/capability contracts: #787, #789)

## Outcome

Package 072's crash-isolation boundary: a pure `WorkerSupervisor` state
machine over worker-process observations, with a bounded restart
policy. A crashing plugin worker is a fact the host observes and
answers by policy — never a reason the control plane dies, and never an
unbounded crashloop.

Transport-free by construction: the host layer (a later PR) launches
real processes, feeds `WorkerObservation`s in, and acts on the
`WorkerDirective` that comes back. Everything here is decidable in unit
tests without spawning anything.

## Rationale

- **The manifest is the contract** (071): only `Application` plugins
  have a worker, so supervision refuses an `AgentContent` manifest at
  construction — the registry verified the manifest; the supervisor
  enforces what it means at runtime.
- **The restart budget is total, not rolling.** A plugin that crashes
  through `max_restarts` lands in `Crashed { exhausted: true }` and
  stays down until a human or an upgrade starts a new session. That is
  the isolation guarantee — no windowed counter can be gamed into an
  infinite loop.
- **Healthy-from-crashed is the restart completing.** The relaunched
  process answering its first probe is the expected next observation,
  not an error. Only exhausted and host-stopped are terminal. (The
  first test run disagreed with the initial transition table — the
  tests were right and the table was wrong; both were corrected
  together before merge.)
- **A stop is deliberate and idempotent.** An exit racing the host's
  stop request is the stop completing — no restart is offered; a
  repeated stop observation is the same single fact. Terminal crash
  states reject a healthy observation with a typed
  `InvalidObservation`: a caller seeing that is working from stale
  state and should hear about it.
