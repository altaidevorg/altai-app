# CP-08-76 — The account model: per-account identity and scoped credentials

- **Package:** 074 — Full Gmail multi-account adapter (PR 1)
- **Status:** in review
- **Depends on:** 070 (#809–#812), 071 (#787, #789), 072 (#815–#818, #820)

## Outcome

The account is now a first-class, durable identity, and it is the
isolation boundary the Gmail adapter (PR 2) will hang everything on:

- **`ExternalAccount`** (protocol): metadata only — organization,
  integration, the provider's stable `account_ref` (the mailbox
  address), display name. Never credential material. Keyed by
  `(integration, account_ref)`: reconnecting the same mailbox keeps its
  `ExternalAccountId` (the stored id survives the reconnect), and two
  accounts at one integration coexist as two rows. An account
  reference is scoped to its integration — the same provider identity
  at another integration is another account.
- **`ExternalObject.account_id`**: the object store's key grows the
  account dimension — `(integration, account, external_id)`. The same
  provider id under two accounts is two objects, never one shared row;
  an object's account never shifts (presenting the same id under
  another account inserts that account's own object and never
  overwrites the first); an unattributed lookup does not see an
  account's object. Pre-074 databases are rebuilt in place (v2 → v3):
  legacy rows survive, stay addressable unattributed, and reopening is
  idempotent — the rebuild never runs twice.
- **`AccountCredentialStore`**: every read and write is addressed by
  `(plugin, account, name)`; values are `SecretString`. Another
  account's scope, another plugin's scope, or another name finds
  nothing — the wrong key does not find the neighbor. Removal is
  scoped: forgetting work's refresh token never touches personal's.
  The host owns the store (the desktop fronts it with its platform
  secret storage); 072's worker hand-off remains the one channel a
  value travels on.

## Rationale

- **Identity before traffic.** Gmail sync (PR 2) is a mapping problem
  on top of 070's engine; what it cannot invent later is the account's
  durable identity and the rule that nothing crosses account lines.
  This PR is exactly that rule, stored.
- **Reconnect ≠ new account.** Keying on the provider's stable
  reference (not a session, not a display name) means OAuth
  re-authorization resolves to the same row and the same objects.
- **Wire-compatible by construction.** `account_id` rides the payload
  with serde defaults, so stored 070 rows decode unchanged; the key
  rebuild backfills from the payload itself.
- **The scope is the address, not a filter.** Credential isolation is
  not "search all secrets, exclude other accounts" — a lookup that
  names the wrong scope simply has no such entry.

## Scope

- `altai-control-protocol`: `ExternalAccountId` typed id;
  `ExternalAccount`; `ExternalObject.account_id` (optional, defaulted).
- `altai-control-plane`: `external_account_repository.rs` (SQLite,
  idempotent upsert keyed `(integration, account_ref)`, 5 tests);
  `external_object_repository.rs` account dimension + v2→v3 rebuild
  (3 tests: two-accounts, account-shift refusal, legacy rebuild);
  `account_credentials.rs` (trait + in-memory store, 5 isolation
  tests); `local_migration.rs` v3 + account table in the lifecycle;
  `external_sync.rs` maps unattributed (single-account) objects.
- No TS mirror: like 070's external types, the account model is
  host-side and does not cross the protocol boundary yet.
