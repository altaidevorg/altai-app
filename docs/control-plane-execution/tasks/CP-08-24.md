# CP-08-24 — Routine cron bridge driver

**Status:** in progress
**Backlog package:** 041 (second PR, completes the package)
**Depends on:** CP-08-23 (package 041 seam: `RoutineMaterializer`)

## Outcome

The second half of the scheduler materialization and cron bridge: a periodic
`RoutineCronBridge` that the daemon spawns, and which on each tick invokes
`RoutineMaterializer::materialize_due(now)`. Recurring routines now flow into the
wake queue without an operator poking the materializer by hand, while the
materializer remains the single tested unit for due-evaluation and coalescing.

The bridge is the managed cron backend. Native deployments do not run this
daemon; the per-attempt native-vs-managed `ScheduleBackend` binding happens
downstream when a routine wake becomes an attempt (no consumer binds it yet, so
this PR does not consult the schedule-backend seam).

## Rationale

CP-08-23 delivered the in-process materialization logic but left it caller-less.
A cron bridge that is never invoked does not bridge anything. This PR supplies
the driver loop and wires it into the daemon, mirroring how
`SingleWriterScheduler` owns `claim_if_eligible` while a separate loop drives it:
the materializer owns the tested logic, the bridge owns only the loop and the
wall-clock `now`.

A failed tick is logged to stderr and the next tick proceeds. One bad tick
(a transient sqlite error, one malformed future routine) must not halt
scheduling for every other routine.

## Scope (this PR)

- `routine_cron_bridge.rs` (NEW): `RoutineCronBridge { materializer, period }`
  with `tick(now)` (single deterministic tick delegating to the materializer) and
  `run(self)` (infinite loop on `tokio::time::interval`, logs errors and
  continues). `DEFAULT_CRON_TICK = 60s` (a recurring routine's finest resolution
  is one minute, so ticking faster only re-evaluates already-coalesced fires).
- `lib.rs`: module + re-export of `RoutineCronBridge`, `DEFAULT_CRON_TICK`.
- `main.rs`: construct `RoutineMaterializer` over the existing routine + wake
  repositories (clones share the same sqlite connections the router uses) and
  `tokio::spawn` the bridge.
- `Cargo.toml`: add the tokio `time` feature (for `tokio::time::interval`).
- No transport route, no scheduler changes, no schedule-backend consultation.

## Invariants

- The dispatch path is unchanged: the bridge only enqueues wakes; the
  single-writer scheduler remains the sole claimer (CP-08-23 invariant preserved).
- At most one wake per due routine per period (materializer invariant; the
  bridge does not bypass coalescing).
- A failed tick never aborts the loop or other routines' materialization.
- The bridge shares the daemon's sqlite connections via `Arc` clones; one writer
  per table remains serialized by each repository's mutex.
