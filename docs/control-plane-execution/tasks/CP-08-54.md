# CP-08-54 — Embedded agent registry and lifecycle commands

**Status:** complete
**Backlog package:** 064 (Agents, org chart and profile administration) —
PR 1 of 2
**Depends on:** CP-08-50–53 (Work OS surfaces over the embedded store),
the agent lifecycle and org-chart semantics established by package 032
(#748, #749)

## Outcome

The embedded host now owns a durable agent registry in `work.db`:

- **Schema v4** adds an `agents` table (id, name, status
  `active|paused|terminated`, self-referencing `reports_to`,
  created/updated timestamps, `agents_status` index). Migration stays
  fail-closed on newer schemas; a real v3 database upgrades without
  losing Work data.
- **Lifecycle mutations are store commands**, not UI state:
  `create_agent` (trims, requires a name, validates the reporting line),
  `transition_agent_status` (terminated is final — only an idempotent
  same-status replay is accepted after termination), and
  `set_agent_reporting` (clears or moves the reporting line).
- **The org chart is acyclic by construction.** A reporting move walks
  the `reports_to` chain upward inside the same transaction and rejects
  self-reference, direct inversion, transitive cycles, and unknown
  managers before anything is written.
- **Host surface**: Tauri commands `agent_list` / `agent_create` /
  `agent_transition` / `agent_set_reporting` with camelCase DTOs, plus
  `AgentRecord` / `AgentStatusInput` in the host contract and `native`
  bindings. The admin UI is package 064 PR 2.

## Rationale

Package 032's agent lifecycle lives in the deployed backend's in-memory
`AgentRepository`; the desktop embeds no such producer, so before this PR
the embedded Work OS had nowhere durable to register an agent at all. The
registry lands in `work.db` — the store the embedded host already owns —
mirroring 032's semantics (terminal-is-final, reporting-cycle rejection)
so the two implementations agree on what a legal org chart is. Mutations
go through store commands because the gate for this package is exactly
that: lifecycle and reporting mutations use control-plane commands, and
the embedded host's control plane is its command surface over `work.db`.

## Scope

- `altai-core work.rs`: `SCHEMA_VERSION` 3→4, `MIGRATION_V4`,
  `AgentStatus` (parse/as_str mirroring `AttemptPhase`), `AgentRecord`,
  `map_agent_row`, store methods `create_agent` / `list_agents` /
  `get_agent` / `transition_agent_status` / `set_agent_reporting`,
  `ensure_reporting_line` helper with a bounded walk.
- `altai-core lib.rs`: re-export `AgentRecord`, `AgentStatus`.
- `altai modules/work.rs` + `lib.rs`: `AgentDto` and the four commands,
  registered after `work_runs`.
- `packages/host-contract types.ts`: `AgentRecord`, `AgentStatusInput`.
- `src/modules/ai/lib/native.ts`: `agentList` / `agentCreate` /
  `agentTransition` / `agentSetReporting` bindings.
- `WORK_OS_PROGRAM_BACKLOG.md`: 064 → `in_progress`.

## Out of scope

- The agents admin surface (registry list, org-chart view, profile
  administration) — package 064 PR 2.
- Cross-agent assignment or routing policy (package 092) — the registry
  records identity and reporting lines only.
- Syncing the embedded registry with the deployed backend's registry —
  the two are separate authorities until a cutover package (stage 10)
  says otherwise.
