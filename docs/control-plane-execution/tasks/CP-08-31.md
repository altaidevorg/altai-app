# CP-08-31 — Governed delivery authorization

**Status:** done
**Backlog package:** 045 (third PR)
**Depends on:** CP-08-25/26 (package 042 approvals), CP-08-30 (package 045 completion gate)

## Outcome

Closes the second clause of the 045 gate — **"delivery actions are governed"** —
with a `DeliveryGate` that authorizes a delivery action for a Work item only
when a governing approval exists in the same organization, carries the
`Delivery { work_item_id }` scope, is decided `Approved`, and was granted for
exactly the payload revision being delivered.

This closes package 045: completion is evidence-gated (CP-08-30) and delivery
is approval-governed (this PR). The gate is an authorization check, not an
enactment: no delivery executor exists yet (package 050 introduces workspace
delivery), so — like the budget enforcer — the gate evaluates and answers; the
executor that performs deliveries will be required to ask.

## Rationale

Package 042's gate is "Decisions bind scope and payload revision; audit is
immutable." The approval store already binds an approval to a scope and a
`payload_revision`; what is missing is a scope that names a delivery and a
reader that turns those facts into an authorization decision. The
`ApprovalScope` doc-comment says further scopes "land with the packages that
introduce them" — this is that package.

The payload-revision match is the safety property: an approval granted for
revision 1 must not authorize delivering revision 2. A pending or denied
approval never authorizes; the gate reports every reason it did not authorize
so the caller can explain the hold.

Multiple approvals may target one work item (ids differ); delivery is governed
when **any** of them authorizes. Blockers are collected across the matching
approvals so an operator sees each hold, mirroring the completion gate's
blocked reasons.

## Scope (this PR)

- `altai-control-protocol/src/approval.rs`: add
  `ApprovalScope::Delivery { work_item_id: WorkItemId }` (serde `kind`-tagged,
  snake_case — same shape as `Plan`).
- `altai-control-plane/src/approval_repository.rs`: add
  `list_in_org(&OrganizationId) -> Vec<Approval>` to the trait and the SQLite
  implementation (org equality filter — mirrors `BudgetRepository::list_in_org`).
- `altai-control-plane/src/delivery_gate.rs` (new): `DeliveryGate` holding
  `Arc<dyn ApprovalRepository>`.
  - `authorize(&self, organization_id, work_item_id, payload_revision) ->
    Result<DeliveryDecision, DeliveryError>`.
  - `DeliveryDecision::Authorized { approval_id }` when a same-org,
    matching-scope, `Approved`, matching-revision approval exists.
  - `DeliveryDecision::Blocked { blockers }` otherwise, one blocker per
    matching approval that did not authorize
    (`ApprovalPending`, `ApprovalDenied`, `PayloadRevisionMismatch`), or a
    single `NoApproval` when none match the scope.
  - `DeliveryError` wraps `ApprovalError`.
- `lib.rs` exports. No storage migration (scope variants serialize inside the
  existing payload JSON; `list_in_org` filters in the mapper).

## Out of scope (follow-up packages)

- The delivery executor itself — recording performed deliveries, one-shot
  consumption of an authorization (package 050 workspace delivery).
- Transport route exposing the gate.
- Scheduler/monitor invocation.

## Invariants

- A delivery action is authorized only by an approval in the same organization.
- An approval authorizes only the payload revision it was granted for.
- A pending or denied approval never authorizes; the gate explains why.
- The gate never mutates anything — it reads the approval audit and answers.
