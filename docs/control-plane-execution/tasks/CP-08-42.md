# CP-08-42 — Plugin registry and upgrade disclosure enforcement

**Status:** complete
**Package:** 071 (plugin model) — PR 2 of 2
**Depends on:** CP-08-41 (plugin manifest contract)

## Outcome

An org-scoped registry that durably stores validated plugin manifests and
enforces the upgrade disclosure rules established in CP-08-41. Installing a
manifest is no longer a client-side assertion: the control plane owns the
record and decides whether an install is a first registration, an idempotent
repeat, an upgrade, or a rejected attempt.

## Rationale

Package 071 separates the manifest *contract* (what a valid plugin declares)
from the manifest *record* (what an organization actually has installed).
CP-08-41 shipped the contract; this task ships the store. The security-critical
rule is that capability expansion can never land silently: an upgrade that adds
capabilities is only committed when the caller explicitly accepts the
disclosure. Downgrades and divergent same-version rewrites are refused outright
so a stored manifest is append-only in intent — versions move forward or the
operation fails.

## Scope

- `plugin_registry.rs` (altai-control-plane): `PluginRegistry` trait
  (`install`, `get`, `list_in_org`) with typed
  `PluginRegistryError` and `PluginRegistryOutcome`.
- `SqlitePluginRegistry` over a `control_plane_plugins` table keyed by
  `(organization_id, plugin_id)` storing the serialized manifest — insert-only
  first registration, guarded UPDATE for upgrades, following the approval
  repository's immediate-transaction pattern.
- Install semantics:
  - first install → validate → store → `Installed`;
  - byte-identical re-install → idempotent `Installed`;
  - version did not advance (lower **or** equal-with-divergent-manifest) →
    `VersionDidNotAdvance`;
  - advance without capability changes → `Upgraded` with disclosure;
  - advance + expansion + `accept_expansion=false` → `ExpansionNotAccepted`
    (row untouched);
  - advance + expansion + `accept_expansion=true` → `Upgraded` with
    disclosure;
  - invalid manifest → `InvalidManifest` before any storage.
- Transport: `POST /v1/plugins` (body: organization_id, manifest,
  accept_expansion) and `GET /v1/organizations/{organization_id}/plugins`,
  both bootstrap-gated; wired as the 13th repository on
  `router_with_control_repositories`; daemon opens the SQLite registry on the
  work database.

## Out of scope

- Runtime capability enforcement (jobs/webhooks execution) — later packages.
- Deletion/uninstall — no package asks for it yet.
- Cross-org marketplace listing or signing.

## Invariants

- Registry rows are per-organization; no read or write path crosses orgs.
- Stored manifests are always valid (validated before insert or update).
- A committed upgrade either advanced the version without adding
  capabilities, or added capabilities only with explicit acceptance.
- Concurrent installs serialize through an immediate transaction; the loser
  re-reads and applies the same rules against the winner's row.
