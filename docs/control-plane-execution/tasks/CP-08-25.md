# CP-08-25 — Approval/decision contract and immutable audit store

**Status:** in progress
**Backlog package:** 042 (first PR)
**Depends on:** package 035 (event translation and attempt finalization — met)

## Outcome

The first half of approvals and governance: a durable `Approval` (governance
decision request with explicit scope and payload revision) and an immutable
`ApprovalDecision` audit record, with an insert-only repository. An approval is
decided exactly once: the first writer wins, an identical re-decision is
idempotent, and a divergent re-decision is rejected so the audit never contradicts
itself. The aggregate advances its `outcome`, `resolved_at`, and `revision` only
on a genuinely new decision.

This PR is the seam — no transport route, no wake enqueue, no execution-phase
mutation yet (follow-up PRs in the package wire the request/resolve flow to the
`awaiting_plan_approval` phase and the `ApprovalResult` wake source).

## Rationale

The protocol already carried `ApprovalId`, an `ApprovalTransitioned` event, the
`awaiting_plan_approval`/`awaiting_approval` execution phases, and an
`ApprovalResult` wake source — but no approval contract or store. Package 042's
gate is "decisions bind scope and payload revision; audit is immutable." This PR
lands the contract and the immutable-audit store in isolation, mirroring how
package 040 began with routine/revision contracts before the cron bridge consumed
them. Keeping the store insert-only (no `UPDATE` of the decision row, first-writer
wins) makes the audit provably immutable.

## Scope (this PR)

- `altai-control-protocol/src/approval.rs` (NEW): `Approval`, `ApprovalScope`
  (`Plan { attempt_id }` for now), `ApprovalOutcome` (`Approved`/`Denied`),
  `ApprovalDecision` (immutable resolution). Re-exported from the protocol crate.
- `altai-control-plane/src/approval_repository.rs` (NEW): `ApprovalRepository`
  trait + `SqliteApprovalRepository`. Tables `control_plane_approvals` (anchor)
  and `control_plane_approval_decisions` (immutable audit, PK = `approval_id`,
  one decision per approval). Methods: `create`, `record_decision`, `get`,
  `get_decision`, `list_pending`.
- `lib.rs` (protocol + control-plane): module declarations and re-exports.
- No transport route, no scheduler, no wake integration.

## Invariants

- An approval is decided at most once; the decision row is insert-only.
- Re-recording an identical decision is a no-op (the aggregate does not advance
  again).
- A divergent decision for an already-resolved approval is rejected
  (`Conflict`); the stored decision and outcome are unchanged.
- `create` is idempotent on an identical approval and fails closed (`Conflict`)
  on a divergent one occupying the same id.
- `list_pending` returns only approvals with no recorded decision.
