# CP-08-39 — Durable activity stream and protocol serving

**Status:** complete
**Backlog package:** 060 (first PR)
**Depends on:** CP-08-37 (package 051 accepted — dispatcher and query contracts), CP-08-25/26 (042), CP-08-27/28 (043), CP-08-32/33 (044)

## Outcome

First half of the 060 gate — **"Server projections, not frontend store joins,
answer operational queries"** — delivers the durable activity stream and makes
the protocol serve it. An append-only `ActivityEventRepository` (SQLite,
org-scoped, cursor-paginated, filterable by kind and work item) becomes the
audit feed; the `ProtocolDispatcher` serves `QueryActivity` end-to-end and
flips the `activity_audit` capability from typed-denial to served. The daemon
wires the store into `work.db`, so operational queries get real answers on
every surface through one seam.

## Rationale

CP-08-37 left `QueryActivity` as a capability-gated typed denial because no
producer existed. This PR adds the producer's foundation: the append-only
store. Audit events are facts — the store is insert-only with idempotent
re-append (same `event_id` + identical payload is a no-op; divergent payload
for a known `event_id` is a `Conflict`), org-isolated by construction, and
ordered by a per-store monotonic sequence that doubles as the pagination
cursor.

Serving goes through the existing dispatcher, not a new path: the
`QueryActivity` arm gains the store and answers `PageResponse<ActivityEvent>`;
capability advertisement derives from the same wiring (`activity_audit` is
true exactly when the store is attached), so the CP-08-36 invariant — nothing
advertises what it cannot serve — holds by construction. Conformance tests
extend to the success path: the same query through the local dispatcher and
the HTTP router yields equal pages.

Projection builders that derive read models from the stream (inbox, work
rollups) and the `ControlEvent` replay store (`event_replay`) remain the
second PR.

## Scope (this PR)

- `altai-control-plane/src/activity_repository.rs` (new):
  `ActivityEventRepository` trait — `append(&ActivityEvent)` (idempotent,
  `Conflict` on divergent re-append) and `query(&ActivityQueryRequest) ->
  PageResponse<ActivityEvent>` (org-scoped, optional `kind`/`work_item_id`
  filters, cursor pagination via the monotonic sequence, `effective_limit`).
  `SqliteActivityEventRepository` over `control_plane_activity_events`
  (`sequence INTEGER PRIMARY KEY AUTOINCREMENT`, `event_id` unique,
  denormalized `kind`/`work_item_id` filter columns).
- `capabilities_from_wiring` gains the activity store flag → `activity_audit`.
- `ProtocolDispatcher` holds `Option<Arc<dyn ActivityEventRepository>>` and
  serves `QueryActivity` when present; absent store keeps the typed denial.
- `router_with_control_repositories` gains the activity repository parameter;
  the daemon opens it on `work.db`.
- Tests: store idempotency/conflict, org isolation, filters, pagination and
  limit clamping; conformance for `QueryActivity` success on both transports;
  capability advertisement follows wiring.

## Out of scope (follow-up PRs)

- `ControlEvent` append/replay store and `event_replay` serving (060 PR 2).
- Projection builders and read models (inbox, board rollups) (060 PR 2).
- Domain recorders writing transitions into the stream (enactment with the
  projection consumers).
- Activity retention/compaction policy.

## Invariants

- The stream is append-only; appends are idempotent per `event_id` and never
  mutate history.
- Queries never cross organization boundaries; the request's organization is
  the only scope.
- The pagination cursor is the monotonic sequence — pages are stable and
  resumable.
- `activity_audit` is advertised exactly when the store is wired; the denial
  path stays reachable and typed.
