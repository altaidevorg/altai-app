# Task Packet: M2-00-01 — Federated control-plane architecture fence

```yaml
task_id: M2-00-01
title: Supersede M1 local-only control-plane constraint and register upstream adoption boundaries
risk_tier: A
status: ready
depends_on: []
objective: |
  Align altai-app architecture records with the canonical federated Work OS:
  a global control plane owns global PM/governance/collaboration fields and
  local work.db owns exact execution facts. Establish upstream provenance and
  licensing gates before importing external source.

  - Moving existing Work mutations to a new service
  - Adding a dependency, submodule, binary or upstream source
  - Changing the shipped M1 Work lifecycle
allowed_files:

  - docs/control-plane-execution/CONTEXT.md

  - docs/control-plane-execution/tasks/M2-00-01.md
  - docs/upstream/UPSTREAM_ADOPTION.md
invariants:
  - Every field has one authority; no last-write-wins.
  - Local work.db continues to own exact Attempt/run/recovery evidence.
  - IsanAgent remains an execution backend and never owns PM state.
  - Macro source has a hard legal gate before it enters an Apache artifact.
acceptance:
  - ADR 0003 no longer prohibits the global control plane.
  - The authority map distinguishes global fields and local execution facts.
  - Every selected upstream has revision, license, intended boundary and gate.
  - The next code task begins with authenticated registration/health rather
    than moving a Work mutation prematurely.
stop_conditions:
  - A proposed upstream license/distribution path conflicts with Apache-2.0.
  - A migration requires both databases to authoritatively write one field.
```

## Handoff

The next implementation packet creates a minimal authenticated control-plane
service and host registration/health contract. It must define the transport,
credential custody, protocol negotiation and control-db bootstrap without
migrating legacy Work writes in the same change.
