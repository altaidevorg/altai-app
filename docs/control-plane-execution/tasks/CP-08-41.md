# CP-08-41 — Plugin manifest and capability contracts

**Status:** complete
**Backlog package:** 071 (first PR)
**Depends on:** CP-08-36/37 (package 051 — versioned contracts and capability negotiation patterns)

## Outcome

First PR of the 071 gate — **"Agent-content and application plugins are
distinct; upgrades disclose capability expansion"** — delivers the manifest
contract both plugin kinds share. `PluginManifest` declares identity, kind,
numeric version, and capabilities; validation makes the kind distinction
structural (an agent-content plugin declares no runtime capabilities; jobs,
webhooks, scoped secrets and plugin UI are application-only), and
`PluginUpgradeDisclosure` computes what an upgrade adds and removes so the
registry (PR 2) can refuse a silent capability expansion.

## Rationale

The runtime packages define what a plugin can be: 072 gives application
workers jobs, webhooks, scoped secrets and idempotency; 073 gives them
schema-driven UI whose checks the UI cannot bypass. Agent content —
instructions, prompts, skills — has no worker and needs none of those
permissions. Encoding that split in the type (`PluginKind`) plus
kind-constrained validation means the distinction is checked at the
boundary, not remembered by convention.

Versions order numerically per component (`1.2.0 < 1.10.0`), never by
string. The disclosure is a pure diff over two valid manifests: it reports
added/removed capabilities and whether the version actually advanced, and
`expands_capabilities()` is the predicate the install path will gate on.
Nothing here installs, stores, or executes anything — those are PR 2
(registry and serving) and 072 (worker runtime).

## Scope (this PR)

- `altai-control-protocol/src/plugin.rs` (new): `PluginKind`
  (`agent_content` | `application`) with `allowed_capabilities`,
  `PluginCapability` (`jobs`, `webhooks`, `scoped_secrets`, `plugin_ui`),
  `PluginVersion` (numeric ordering + Display), `PluginManifest` with
  `validate()` (typed `PluginManifestError`: duplicate capability,
  capability-not-allowed-for-kind, empty display name),
  `PluginUpgradeDisclosure` (`diff`, `is_version_advance`,
  `expands_capabilities`).
- `altai-control-protocol/src/id.rs`: `PluginId` (`plugin_id` / `plg_`)
  through the typed-ID macro, registered in the distinct-type test.
- `packages/control-contract/src/plugin.ts` (new): TS mirror — union types,
  `validatePluginManifest`, `diffPluginUpgrade`, `isVersionAdvance`,
  `expandsCapabilities` — exported from the package index.
- Tests on both sides: kind distinction and kind-constrained capabilities,
  duplicate rejection, empty-name rejection, numeric version ordering,
  expansion/removal/pure-bump/downgrade disclosure behavior, serde
  round-trip with snake_case tags.

## Out of scope (follow-up PRs)

- Plugin registry: storing manifests per organization, install/upgrade
  flow that requires the disclosure when capabilities expand (071 PR 2).
- Capability negotiation integration (`ControlPlaneCapabilities` stays
  unchanged).
- Worker runtime, crash isolation, secrets custody (072); schema-driven
  UI (073).

## Invariants

- One manifest declares exactly one kind; runtime capabilities belong to
  application plugins only.
- Capability sets are duplicate-free; a manifest that fails validation is
  data, not an installable plugin.
- Version ordering is numeric per component; a disclosure that reports an
  advance always has `to_version > from_version`.
- Upgrades that add capabilities are detectable (`expands_capabilities`)
  before anything is installed.
