# CP-08-57 — Usage ledger over the agent event journal

**Status:** complete
**Backlog package:** 065 (Governance, approvals, budgets and audit
dashboards) — PR 2 of 2–3
**Depends on:** CP-08-56 (audit feed over `work_events`), package 063
(runs hub: attempts joined with their Work), the delivery loop that
persists every run event to the agent event journal

## Outcome

Cost attribution ships, closing package 065's gate: every
decision/cost/stop is now attributable and drillable. Home's Audit tab
gains a **Feed | Usage** switch, and the Usage view renders the
workspace's token ledger — one row per recent attempt, each naming its
Work and the tokens its chat recorded:

- **Attributable**: each row joins an attempt (with number and phase)
  to its Work and to the chat-bound token totals — prompt,
  completion, total, cache read, cache write — summed from every
  `usage` event that chat journaled.
- **Drillable**: every row opens its Work's detail surface.
- **Honest about absence**: an attempt that never bound a chat reads
  "no chat bound" — a different fact from a bound chat that recorded
  zero tokens, which reads "0 total". The page header sums the
  distinction: attempts · attributed · without a chat · total tokens.

One new read projection backs it:
`EventJournal::chat_usage_totals(chat_ids)` aggregates the journal's
`usage` rows per chat (SUM/COUNT via `json_extract`, malformed payloads
degrade to zero contribution), and `work_usage_recent` joins those
totals to the store's recent attempts through each attempt's `chat_id`
binding.

## Rationale

CP-08-56 deferred cost attribution pending "a usage producer the
embedded host still lacks". Tracing the telemetry path showed the
producer already exists and is durable: the runtime emits
`TelemetryEvent::AgentUsage`, the delivery loop persists every run
event — usage included — to the agent event journal at
`{workspace}/.system_generated/agent_event_journal.db`, in the same
write path as transcripts. Attribution is therefore a read-side join
(attempts ↔ journal chat totals), not new producer wiring and not a
`work.db` schema bump: the exact "producer exists, read side missing"
shape of CP-08-51/52/56.

Cost in USD stays out: the host has no pricing source, so token counts
are the honest ledger — inventing a price table would fabricate
attribution rather than record it.

## Scope

- `altai-core journal.rs`: `ChatUsageTotals` +
  `chat_usage_totals(chat_ids)` (kind = `usage` filter, per-chat
  SUM/COUNT, empty-slice no-op), + test covering multi-event sums,
  non-usage exclusion, and malformed-payload degradation.
- `altai-core lib.rs`: re-export `ChatUsageTotals`.
- `altai modules/work.rs` + `lib.rs`: `WorkUsageDto`/`WorkUsageTotalsDto`
  and the `work_usage_recent` command — recent attempts (limit clamp
  100 / default 20), journal resolved exactly as the desktop host
  resolves it, absent journal = no usage recorded; pure
  `attribute_usage` join keeps bound-zero distinct from unbound. Tests
  cover the join semantics and the journal path (present, absent,
  empty request).
- `packages/host-contract types.ts`: `WorkUsage`, `WorkUsageTotals`.
- `src/modules/ai/lib/native.ts`: `workUsageRecent` binding.
- `work-board/lib/usageLedgerProjection.ts` (+ tests): rows with
  separated token labels, cache line only when cache tokens exist;
  `summarizeUsageLedger` page totals.
- `work-board/UsageLedgerSection.tsx`: load/retry/empty/list surface
  with summary header; rows drill into Work detail.
- `work-board/AuditPanel.tsx`: Feed | Usage switch in the header.
- `WORK_OS_PROGRAM_BACKLOG.md`: 065 → `accepted` (#804–#805);
  dashboard 21→22% overall, 13→15% product/UX; queue advances to
  CP-08-58 (package 066).

## Out of scope

- **Budget enforcement** — the budget engine and `UsageTracker` exist
  but no decision producer consumes them to stop work; that is an
  execution-safety feature (stage-3/4 territory), not attribution, and
  package 065's gate is attribution and drillability.
- **Cost in USD** — no pricing source; token counts only.
- Ledger filtering/search and per-agent rollups — a page of newest
  facts first; aggregation views arrive when the ledger has volume.
