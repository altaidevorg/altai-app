# CP-08-62 — External-object sync engine

- **Package:** 070 — ExternalObject model and GitHub adapter (PR 2)
- **Status:** in review
- **Depends on:** 051, 060 (PR 1: #809)

## Outcome

The control plane can now run an external-object sync: one
`ExternalSyncService` per integration drives a provider's objects into
the durable store from PR 1 and records what happened as `ExternalSync`
activity events with an `Actor::External` — so sync runs are auditable
in the existing audit feed with no new UI. The engine is
transport-free: providers sit behind an `ExternalObjectProvider` trait
the host implements (the GitHub provider is PR 3).

## Rationale

The three gate rules are engine responsibilities, not adapter
responsibilities, so they are enforced once for every integration:

- **Idempotency**: the engine hashes the adapter's canonical mapped
  `content` (sha256) and relies on the store's equal-hash no-op — an
  unchanged provider payload never writes and never emits an event.
- **Authority**: the store's per-object rule decides apply vs. refuse;
  the engine just reports which happened.
- **Conflict reporting**: a refused overwrite lands in the run's
  report (`ExternalSyncConflict` with both hashes) *and* the audit feed
  ("sync refused …: local authority holds …"), so a conflict is a fact
  someone can see, not a swallowed branch.

The `since` watermark is the newest **provider-reported** change
already in the store (`external_updated_at_unix_seconds`), not our own
sync time — a quiet period never widens into a full refetch, and a
provider that reports no change timestamps simply gets a full fetch.

## Scope

- `src-tauri/crates/altai-control-plane/src/external_sync.rs` (new):
  `ProviderObject`, `ExternalObjectProvider`, `ExternalSyncService`,
  `ExternalSyncReport`/`ExternalSyncConflict`, `ExternalSyncError`,
  `content_hash`; registered and re-exported in the crate root.
- Tests (6) against the real SQLite repositories with a fake provider
  whose pages swap between runs: first-run inserts + events, idempotent
  re-run (no writes, no events), changed-content apply under external
  authority, refused overwrite under local authority (report + stored
  content untouched + refusal event), the provider-clock watermark, and
  provider failure surfacing with no partial writes.

## Out of scope

- The GitHub provider itself (mapping GitHub issue/PR payloads over
  the desktop crate's existing GitHub HTTP client) — package 070 PR 3.
- Any UI; sync outcomes surface through the existing audit feed.
- Scheduled sync runs (bridging the engine into a routine/cron cadence)
  — once a real provider exists.
